## 1. 结论与业务范围

现有项目已有三端骨架、真实工具调用路径、分析专家、导演与质检迭代、规则校验、方案存档及 FFmpeg 编译执行。当前最需要深化的是：让剪辑决策建立在可定位、可校验的素材单元上，而不是继续增强自由时间戳 Prompt。

推荐首个闭环：

> 单段语音主导素材 → 版本化语义单元 → 一个主题的候选片段及依赖 → 原始顺序组织 → 程序硬校验与语义风险检查 → 人工编辑和确认指定版本 → 受限渲染 → 人工评测。

不承诺爆款、不承诺一键高质量成片，不做复杂多素材叙事。允许访谈包含多个说话人，但不承诺自动说话人识别；问答依赖不明确时扩大保留范围或交人工处理。

建议第一批素材为 2～10 分钟，输出上限选择 30/60/90 秒；这是拟定实验范围，不是当前性能能力。默认原速、原顺序、硬切、不增删改写口播。画幅和字幕只使用经过编译与渲染测试的能力。

## 3. 实际架构与链路

### 3.1 当前可达主链路

```text
React 上传/分析
  → Java Project/Asset + 本地文件存储
  → AnalyzeTaskService 建 ANALYZE、置 RUNNING、同步 HTTP 提交 Python
  → Python 内存 job + asyncio.create_task
  → 元数据 → 场景 → 抽帧/ASR → Timeline/Narration/VLM → AnalysisReport
  → PlanAgent 普通 for 循环：导演 → QA → 重写
  → sanitize → validator；失败直接返回规则方案
  → Python 进度/完成 HTTP 回调
  → Java 报告存储、方案反序列化、基础校验、版本存档、任务终态
  → React 表单/textarea JSON 编辑 → PUT 保存
  → apply 读取服务端当前方案 → 同步 FFmpeg 分段/拼接 → 下载
```

Java 是 Maven 多模块 DDD 分层：trigger/app/domain/infrastructure/api/types。Python 使用 FastAPI、LangChain；LangGraph 是分析阶段的可选编排。React 使用 Zustand、Ant Design，实际编辑器是 textarea，不是 Monaco；进度实际走轮询，并无可达 SSE 实现。

**默认 local**：Java 仓储内存，视频在本地磁盘；Python `_jobs` 内存。重启后磁盘文件可能还在，但任务/方案元信息不恢复，不能宣称阶段恢复。

### P1：用声学块/抽样镜头承载语义决策，细切依据不可靠

代码：

- [云端 ASR 块时间绑定](file:///E:/java/AgentCut/AgentCut-ai/app/tools/transcribe.py#L152-L169)：调用只取 `resp.text`，TranscriptSegment 时间取音频块 start/end。
- [长语音每 30 秒直接切块](file:///E:/java/AgentCut/AgentCut-ai/app/tools/transcribe.py#L177-L199)：不会按完整句子切分。
- [场景预算直接采样区间](file:///E:/java/AgentCut/AgentCut-ai/app/tools/scene_detect.py#L95-L99)：限制的不只是帧图，还丢弃后续决策所见的源区间。

- `AnalysisReport.transcript_text` 按区间相交取整块文本，裁去部分音频仍可能保留整段字幕。

## 5. 替代方案与取舍

| 方案 | 内容 | 收益 | 代价与不足 |
|---|---|---|---|
| A：现有流程补强 | 修复恢复重叠、fallback 重校验、完整 QA 证据、硬速率上限、区分模式 | 改动最小，可快速修复已知机制缺陷 | 模型仍自由生成时间戳，素材颗粒度问题未解决 |
| **B：受限素材索引闭环，推荐** | 保留现有专家/导演/QA，增加语义单元索引、ID 决策、依赖检查、统一验证与版本确认 | 对准内容定位和筛选问题，可清楚解释 Java/AI 分工并做消融 | 需跨端小幅契约演进；真实时间对齐必须先满足 |
| C：全链路恢复一次性建设 | 索引闭环 + 图 checkpoint + MQ/Outbox + 完整取消/恢复/缓存 | 工程完整度高 | 工期大、错误源多，无法快速判断语义方案是否有效；当前不推荐 |

不因“确定性化不够 Agent”而拒绝程序约束。模型负责语义判断和建议，程序负责合法资源、可执行动作和状态一致性，两者不是冲突。

## 6. 最小闭环设计

### 6.1 五阶段及职责

| 阶段 | 复用/新增 | 产物与边界 |
|---|---|---|
| 理解素材 | 复用 probe/ASR/VLM/分析专家；新增 IndexBuilder | 保留完整源区间，区分镜头与语义单元；记录各工具真实/失败/模拟状态 |
| 发现候选 | 改造现有 Narration 输出，不新增框架或独立 Agent | 一个主题的候选 unitIds、角色、必要依赖及证据；不输出任意时间戳 |
| 组织内容 | 改造现有 PlanAgent 输入/输出 | 选择有序 unitIds 与受限操作；默认原始顺序、原速、硬切 |
| 校验方案 | 复用 validator/QualityAgent，新增映射和依赖校验 | 先硬校验，再语义风险检查；所有修复/降级重新映射和校验 |
| 人工确认 | 复用 Edit/Preview 与版本表 | 所见版本、索引版本和校验结果绑定；确认后渲染固定快照 |

五阶段是业务职责，不等于需要五个新 Agent、五个任务表或完整迁移 LangGraph。

### 6.2 版本化素材索引

建议 `MaterialIndex`：

- `indexId/indexVersion`、`assetId`、源文件内容 hash、duration、timebase。
- ASR/tool/model/config 版本、原始转写引用与覆盖/失败记录。
- 完整镜头列表；VLM 帧采样预算独立控制，不删除索引中的镜头或语义单元。
- `units[]`：unitId、原文、startMs/endMs、timingQuality、边界证据、源转写引用、sceneRefs。
- `dependencies[]`：fromUnitId、requiredUnitIds、类型（定义/指代/条件/否定/问答/因果）、原文证据、来源和置信状态。

ID 在同一索引快照内稳定，重做 ASR/分句/手工对齐生成新版本；禁止把旧 ID 静默映射到新位置。`(indexId,indexVersion,unitId)` 唯一确定资源。同一 asset 的不同索引版本不能混用。

索引结构由 Python 构建，Java 持有持久化引用和准入校验；模型不能修改索引区间。先使用现有分析报告存储保存索引或其引用，不引入向量库。Java 的真实 Asset ID 由请求传入，不能继续以 Python job 派生 ID 充当资源身份。

### 6.3 语义单元与时间对齐

分句依据：ASR 原文、标点、停顿、续句关系共同判断；停顿只提供边界候选。长句的逗号不自动切，跨镜头完整句可跨镜头保留。

关键限制：已有云端 ASR 只返回文本块，标点位置不能直接换算音频时间。禁止按字数均摊后冒充精确时间戳。

最小路径：

1. 优先核实已有本地 FunASR `sentence_info` 在真实素材上能否稳定给出句级对齐。
2. 无可靠句级时间时，保留整个 ASR 块作为低精度候选，标记 `timingQuality=coarse`；块内有多句不允许自动细切。
3. ASR 块边界自身切断语句时合并相邻块；合并仍无可靠边界则进入人工对齐/需检查状态。
4. 小规模基准允许人工对齐，用于独立评估“决策能力”；必须同时报告人工对齐成本，不能把这组结果冒充自动端到端效果。
5. 仅当已有对齐路线被真实验证不足时，再讨论独立对齐组件，不预先更换框架或模型。

无可用语音、严重漏转写、纯视觉/音乐内容，返回 UNSUPPORTED_INPUT 或 NEEDS_INPUT_REVIEW，不使用模拟口播生成可确认方案。每个工具分别记录 provenance；不能仅用 VLM simulated 标志推断整条链路真实。

### 6.4 候选发现与上下文依赖

输入完整单元列表和用户主题，可允许用户先选择建议主题。输出候选集合，标注主题核心、问题/背景、解释、限定条件、结论；每项理由需引用索引原文。

依赖图属于模型辅助提出的语义证据，不是程序自动证明真值。程序能确定性检查“已声明依赖有没有被保留”，不能保证模型没有漏报依赖。

组织流程：

- 从主题核心单元计算已批准依赖闭包，包含必要定义、先行词、问句、条件和否定。
- 补依赖后重新计算时长；不扩大为保护全素材全部论点。
- 依赖环按整体组保留，若整体无法满足预算则拒绝自动方案。
- 未解析指代/不确定依赖 → 邻近上下文保守扩展 + NEEDS_REVIEW，不把模型置信分数当语义证明。
- QA 看到原始选中单元、删去的邻接单元和依赖证据，能够指出声明遗漏；high 原意/上下文风险未解决时不进入确认。

### 6.5 轻度精剪与主题提炼

`mode=TOPIC_EXTRACT` 为本轮推荐模式：允许删掉与选定主题无关的完整单元，不使用固定保留比例；保留选题的核心及依赖，不强保所有高重要论点。

`mode=LIGHT_TRIM` 后续接入：默认保留全部内容，仅删除明确确认的静音/重复/口误完整单元；不能把主题提炼策略隐藏在 fast/style 中。

首版 TOPIC_EXTRACT 使用原速。后续才讨论有界变速作为用户显式选择的软策略；速度上限应基于可听性测试，不沿用 2.5 当质量合理值。

### 6.6 硬约束、软目标与不可行

硬约束：

- 合法资产/索引版本/单元 ID；区间合法、无重复，无未经允许的重排。
- 人工 lockedKeep/lockedDelete 不被模型覆盖；明确依赖闭包满足。
- 受限操作、参数范围、非空可渲染 timeline、字幕在输出时间域内。
- 用户显式要求的 maxDuration 为上限；默认原速；真实帧/音频边界由程序映射。
- 无未经披露的模拟或不完整分析结果进入可确认状态。

软目标：主题覆盖、语义连贯、节奏、目标时长接近度、少修改。用户期望 60 秒不等于必须填满 60 秒。

冲突顺序：合法与安全 → 人工锁定 → 已确认的信息依赖完整性 → 可配置目标。硬上限与锁定冲突，不静默违反任何一项。

输出：

- `FEASIBLE`：程序硬校验通过，仍需人工内容确认。
- `NEEDS_REVIEW`：有可展示建议，但边界或语义风险未消除，不能直接确认渲染。
- `INFEASIBLE`：当前候选空间无法同时满足硬约束，附冲突 ID、相关依赖和已计算时长下界。
- `FAILED/UNSUPPORTED_INPUT`：执行失败或输入不支持，保留诊断。

有限搜索未找到方案时返回 `NO_FEASIBLE_CANDIDATE_FOUND`，不能宣称已数学证明全素材无解。只有锁定内容与必需依赖的确定下界超上限等情况，才返回可证明的时长冲突。

### 6.7 有限迭代与最佳候选

建议沿用最多 3 轮作为首版配置，不新增循环框架。维护统一 deadline、调用计数和 token/成本累计；每次调用前计算剩余预算，调用超时与重试不得重新获得整份预算。

顺序：

```text
DirectorDecision → 服务端索引映射 → 硬校验
  → 合格候选快照保存
  → 原文证据 QA
  → 受限修复（仅 unitIds/受限操作）
  → 重新映射与全量校验
```

bestCandidate 只在硬合格池中选择。分数只是排序辅助；high 原意风险优先于分数，不能用 `passed OR score` 绕过问题。最后一轮失败保留此前合格快照，预算耗尽返回降级原因和未解风险。

QA 不可用：有硬合格候选则展示为 NEEDS_REVIEW 并标记质量证据缺失；无合格候选则失败。没有候选时不能把未经全量验证的规则兜底包装为成功。

每份质量报告绑定 candidateHash/validatorVersion；修复、fallback、编辑后旧报告失效。规则 fallback 和正常方案经过同一门禁。

### 6.8 方案、编辑、确认与渲染契约

保留现有 Plan 为“程序生成的可执行文档”，另定义受限 `DirectorDecision`，不把模型的决策 JSON 直接当 FFmpeg 方案：

- Decision：indexVersion、selectedUnitIds、必要依赖声明、受限可选操作，不含 source.url、自由 sourceRange、命令、filtergraph、codec。
- Mapper：用服务端索引映射到现有 timeline，回填 Asset 元数据、字幕和输出参数。
- PlanContext/Envelope：归档 revision、index 引用、内容 hash、决策证据、约束、校验版本和状态；作为元信息，不混淆现有 schemaVersion。

三端对 Envelope 与 Plan 明确区分。先用现有版本表和分析报告存储扩展元信息，避免同时建立另一个“方案系统”。如需扩展 Plan Schema，显式升版本并保留旧 1.0 读取，不偷偷添加 additionalProperties:false 之外的字段。

编辑规则：普通界面选/删/锁单元，时间来自索引；JSON 高级编辑也必须服务端校验。若允许人工细调边界，先形成带来源的新索引单元/版本，再引用它，不允许直接绕过 ID 约束。

版本规则：

- `revision` 是服务端递增归档号，返回保存结果；避免持续展示模型写死的 planVersion=1。
- 保存携带 expectedRevision，冲突返回 409；历史不可 upsert 覆盖。
- 回滚读取历史并生成新当前 revision，不修改旧历史。
- 确认绑定 revision + indexVersion + planHash + constraintsHash + validatorVersion；服务端重新读取、校验、生成确认记录。
- apply 接受确认 ID/指纹与指定 revision，原子创建渲染任务并固定快照。待执行时版本已变更则拒绝旧确认；任务已准入后允许渲染旧快照，并明确标记其版本，不能换成最新内容。

最小渲染边界：

- 支持 keep/delete；字幕仅在有可靠对齐且契约测试通过时启用；默认原速、硬切。
- 既有 speed/crop/volume/mute 能力保留，但未经本闭环验证的不对模型开放。
- transition/BGM、codec/bitrate 未执行的参数应明确拒绝，不能接收后静默忽略。
- 每个 task 使用独立目录，固定输入资产和输出文件；旧任务下载不被新渲染覆盖。
- 文件路径只来自可信仓储；白名单可执行文件/操作/参数，禁止任意命令/URL/filter 字符串；drawtext 采用文本文件及明确转义，字体颜色位置受限。
- 验证 ffprobe 时长、音轨、尺寸及字幕对齐。不能仅凭 exit=0 判断成片合格。

## 7. 复用任务体系的可靠性演进

### 7.1 首个闭环必需

- 进度更新只允许 RUNNING、匹配当前 attempt 的任务；终态不能被迟到 progress 复活。
- 保存提交时完整目标、asset/index 版本、baseRevision、requestId；记录 Python jobId。
- Python 返回非 2xx、非法受理响应、提交异常 → 明确失败，不能仅读取 body 后等待看门狗。
- 回调包含 taskId/runId/attempt/eventId/sequence/resultHash；身份校验，重复/乱序事件按条件更新。
- Java 用同一事务原子完成回调认领、报告/候选保存、方案 revision 更新、终态更新；并发只一个成功。
- 老分析结果与用户新编辑冲突时保留为候选分支，不覆盖当前方案。
- MySQL 用 row version/CAS 或行锁实现更新；内存模式使用项目/任务级原子临界区，并明确单进程演示限制。

事务内只做短写入，不包住模型调用或 FFmpeg。若当前 revision 冲突，则保存任务产物但不推进当前版本。看门狗与完成回调使用同一个条件终态更新接口，防止交错覆盖。

### 7.2 后续阶段恢复，不另造任务调度系统

在既有 Task 增加 stage、attempt、lease、inputHash、artifactRef 等元信息，Java 为控制状态权威；Python 为可重入执行器。阶段产物可存现有持久化报告或受控文件存储，带 manifest/hash，成功写入和校验后再提交阶段完成。

第一批 checkpoint 只选 INPUT_INDEX_READY 和 CANDIDATE_READY，避免为每个抽帧/小调用建持久化节点。恢复从最后一个输入版本一致、hash 校验通过的产物重启后续阶段，不等于从模型调用中间 token 继续。

Java 持久化 PENDING 任务作为可扫描工作项，后台 worker 领取 lease；Python 受理以 runId/attempt 幂等。HTTP 超时存在“已受理但 Java 未收到响应”的不确定性，靠相同请求标识去重，不能盲目新建 job。

建议复用现有任务表加轮询领取，不立即上 MQ/Outbox。未来确实需要跨节点高吞吐再讨论 MQ；不能引用现在的 outbox_event 表宣称已有可靠消息能力。

取消分成业务与物理：CAS 标记取消、禁用晚到结果；执行器在阶段/调用边界检查。正在同步网络调用可能不能立即终止，需要报告剩余成本；FFmpeg 记录进程句柄并有超时终止。恢复测试必须在 mysql 模式完成，local 只证明逻辑，不宣称重启持久恢复。

### 9.2 素材集与标注

建议先用 12 段授权/自制素材：8 段开发、4 段冻结留出；含普通讲解、定义后指代、条件/否定、因果铺垫、跨停顿长句、问答依赖、重复冗余及低 ASR 质量。不能随机拆同一视频片段到训练/测试，避免上下文泄漏。

素材集固定文件 hash、版本、转写/对齐来源、目标主题与时长、关键内容及依赖、人手锁定约束。多人标注分歧单独保留；小样本结论只适用于本素材集。

每个素材预先标注任务相关关键单元和必要依赖，不要求主题提炼保留全视频所有信息。人工观看原片及成片评“是否改变选定主题原意”，而不是按删减比例评。

### 9.3 三条真实基线与公平性

1. **简单规则**：明确固定规则，例如同一 ASR 索引下关键词命中扩展邻接单元、原序原速、预算内选择；禁止用目标人工标签生成规则方案。
2. **单 Agent**：固定分析输入，一次导演决策，无 QA 重写；记录失败与非法输出，不隐藏失败样本。
3. **当前多 Agent**：冻结当前工作区策略，在真实 ASR/VLM 环境运行；保留原始结果、门禁失败及 fallback，不把失败删除后只展示成功。

新增策略作为第四组。区分两个实验：

- 决策隔离实验：共享同一真实/人工对齐索引、主题和约束，比较决策；人工索引的人工成本单列。
- 自动端到端实验：所有工具真实执行，包含 ASR/VLM 失败和对齐成本，比较真实用户体验。当前方案可能生成硬约束非法结果，照实计入违反率。

模型/版本、输入、温度、重试、预算均记录。每素材每策略建议 3 次真实运行，至少固定相同重复次数；预算不足减少策略而不只挑最佳一次。所有组使用相同输出目标，原速对比和既有自由变速结果分开报告。

### 9.4 消融与指标定义

按基线发现再选消融，不全量组合爆炸：ASR-only 对比 ASR+VLM；QA 开关；上下文依赖保护开关；自由时间戳对比 ID 映射。一次只改变一个变量，其他预算一致；关闭语义保护也不得关闭基本执行安全门禁。

| 层级 | 指标 | 定义/分母 |
|---|---|---|
| 执行 | 硬约束违反率 | 所有生成结果中违反至少一条硬约束的比例；另报按规则数量 |
| 执行 | 可执行率 | 实际 FFmpeg 渲染成功且 ffprobe 校验通过 / 所有已准入渲染方案；另报准入率 |
| 执行 | 任务完成率 | 截止预算内完成目标产物 / 全部受理任务；不可行与失败单独分类 |
| 执行 | 恢复正确率 | 故障后正确恢复且无重复提交/版本覆盖 / 全部故障注入任务；仅 P3 后报告 |
| 内容 | 关键内容误删率 | 被删除的任务相关关键单元 / 人工标注关键单元；按素材和总量都报告 |
| 内容 | 上下文缺失率 | 存在至少一处必要依赖缺失的成片 / 全部可播放评测成片 |
| 内容 | 原意改变率 | 人工确认至少一处条件/否定/因果/指代原意改变的成片 / 全部可播放评测成片 |
| 用户 | 素材定位时间 | 从任务开始到找到可用主题片段的实际时间；包含查证与失败重试 |
| 用户 | 人工修正时间 | 从初稿出现到用户确认的活跃操作时间；等待模型/渲染单列 |
| 用户 | 修改次数 | 预定义选择/删除/补上下文/边界调整操作数，避免前端细粒度事件虚增 |
| 成本 | 耗时/调用成本 | 阶段耗时、总耗时、请求/重试数、实际 token usage、计价版本；缺 usage 标未知 |
| 稳定 | 降级与失败 | provenance、fallback原因、失败阶段、预算耗尽、不可行、需人工检查，均含分母 |

模型评分只作为诊断字段，不进入主要效果指标。内容指标应同时报告“系统交付覆盖率”，防止通过拒绝所有困难样本降低误删率。

用户小试建议 3～5 名参与者，同主题复杂度匹配任务，交叉平衡先后顺序，避免重复看同一视频的熟悉度收益。样本不足报告原始配对值与中位数，不宣称统计显著或普遍创作者收益。

### 9.5 必测异常

- ID 不存在/重复/过期版本；错误 asset；模型伪造源 URL/时间戳/未知操作；额外字段。
- 场景很多但索引覆盖完整；跨镜头句、连续 65 秒语音、块边界切词；缺词时间对齐不能假精确。
- 保留代词但删先行词；删定义/否定/条件/问句；依赖环；用户锁删必要上下文。
- 锁定与时长矛盾；无可行候选；全部删除；倍速数量/上限；字幕时域与帧率并非 30。
- 第三轮失败仍返回此前硬合格候选；最高评分方案非法；QA 挂掉；修复后重叠；fallback 重校验。
- SUCCESS/FAILED 后迟到 progress；重复完成、并发完成；看门狗与完成交错；Java 提交超时但 Python 已受理。
- 双编辑 expectedRevision 冲突；回滚后旧确认；用户新编辑后旧分析到达；渲染准入后继续编辑。
- 同项目和跨项目并发渲染；历史下载不变；字幕含引号/冒号/换行；资源路径越界；输入无音轨/损坏。
- P3 才执行：checkpoint 写一半、manifest/hash 错误、Java/Python 被杀、lease 过期、取消后回调到达。

### 9.6 验收门禁与效果发布

工程验收：上述确定性非法输入全部拒绝，最终可确认结果全量校验；终态不复活、历史不可覆盖、确认与渲染快照一致；真实小样本准入方案全部通过实际渲染检查。这是测试集验收目标，不宣称全输入绝对正确。

内容验收：冻结风险样本中已标注的必要依赖全部保留，已知否定/指代/句子切断风险不进入无告警确认。人工确认不是系统语义正确的证明，仍须独立成片评估。

效果发布：不预设提升百分点；新方案若在留出集发生关键原意回归，不替代旧策略；若人工修正时间没有观察到收益，报告未证实而非写质量提升。数据量不够时只公布逐样本结果和限制。

### 10.2 后续完成后可使用的叙事结构

- **业务问题**：创作者定位主题和手动补上下文耗时，直接压缩素材易改变原意。
- **设计取舍**：模型识别主题与依赖，程序负责合法 ID、时间映射、硬门禁和版本一致性；复用现有任务，不为技术栈数量新增框架。
- **异常边界**：不确定对齐不细切；锁定冲突明确不可行；晚回调不覆盖；取消与恢复有成本/状态边界。
- **验证结果**：填写真实素材版本、实验组、样本量、成功/降级/失败及人工修正观测值，不填模型自评分。

常见追问：

**为什么已有 Schema 还要 Clip ID？**  
Schema 保证结构，不能证明时间戳来自真实素材；ID 将可选空间绑定可校验索引。但索引错误仍需对齐测试。

**为什么 LangGraph 不等于恢复？**  
现在只是内存图编排；需要持久化产物、输入版本、幂等推进和重启领取，不能靠依赖安装证明。

**上下文依赖能不能完全确定性？**  
已声明依赖的覆盖可以确定性，漏报依赖和原意判断仍需原文 QA、保守降级、人工评测。

**如何保证 exactly once？**  
保证结果提交和当前版本推进的幂等/CAS；模型/外部调用可能重复，不宣称全链路 exactly-once。

**三 Agent 是否优于一个？**  
只有同素材同目标的真实对照能回答。QA 的增加也带来成本和相关性错误，必须做消融。

**为什么不直接 MQ/新框架？**  
当前首要瓶颈是决策依据与门禁一致性。已有任务表可扩展 lease 和阶段产物；业务规模证明需要后再演进。

### 10.3 暂不能写入简历

剪辑质量提升百分比、人工成本下降比例、持久化恢复、MQ/Outbox 可靠调度、端到端 exactly-once、完整语义保护、版本绑定确认、支持全部 Schema 操作、自动成片已验证、服务承载量/QPS。只有实现并按对应实验验证后才能改为成果。

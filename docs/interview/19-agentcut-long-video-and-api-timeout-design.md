# AgentCut 长视频处理与模型 API 超时设计补充

## 1. 结论与范围

两类问题需要一起考虑：

1. 长视频增加媒体处理、模型输入和调用数量，容易超时、资源耗尽或中途失败。
2. 外部模型 API 超时存在结果不确定性，重试可能重复生成、重复计费和产生晚到结果。

推荐方向：

> 明确剪辑目标 → 有范围的分析或全片粗索引 → 候选精分析 → 有界并发与共享预算 → 保存合格产物 → 受限重试与版本化结果提交。

不能靠统一延长超时、无限分段并发或增加 Agent 数量解决。

当前首版仍是单段口播/访谈生成脚本。电影涉及动作、人物关系和跨场景剧情，属于后续独立业务扩展；只使用授权素材。设计考虑电影不等于当前已支持电影剪辑。

## 2. 需要回答的边界问题

### 2.1 长视频

- 用户要找某类片段、某角色出场、剪一场戏，还是总结完整剧情？
- 超长输入在什么阶段被拒绝或要求缩小范围？
- 全片粗分析会漏掉哪些对白之外的视觉事件？
- 一个块失败，哪些后续结果仍能使用，是否需要重新分析全片？
- 分段边界切断对白、动作或剧情铺垫时如何发现？
- 同一视频换主题时，哪些产物可以复用？
- 并发增加后，是资源吞吐变好，还是模型限流与重试变多？
- 仅分析部分区间的结果，如何避免被理解成全片最佳方案？

### 2.2 模型 API

- 超时发生在连接、等待首响应、流式读取还是总调用期限？
- 服务商是否已经执行，是否提供请求 ID、异步状态查询或幂等能力？
- SDK、HTTP 客户端与业务层是否都有自动重试？
- 一次重试还能使用多少剩余任务预算？
- 本地取消后，服务商或后台线程是否仍在执行？
- 部分响应是否完整，是否有结束状态、截断或合法性错误？
- 超时结果晚到时，是否还能写入当前任务或覆盖新候选？
- 重复调用的成本能否确认，未知费用如何呈现？

## 3. 长视频处理的三种路线

| 路线 | 适用场景 | 取舍 |
|---|---|---|
| 用户指定范围 | 剪某场戏或已知片段 | 最易落地，人工定位成本单列 |
| 全片分段精分析 | 需要较完整内容覆盖 | 成本高，受资源、限流与上下文整合约束 |
| 全片粗索引，候选精分析 | 有明确主题的长视频选材 | 推荐演进方向；降低昂贵分析范围，但存在漏召回 |

完整剧情总结不能直接套用“关键词找片段”。对白检索也不能独立覆盖动作、表情和无对白事件。

建议先验证指定范围，再做目标驱动全片索引；全片剧情线最后考虑，不提前扩大首版承诺。

## 4. 粗到细分析与素材索引

### 4.1 全片粗索引

提取媒体信息、对白/授权字幕、镜头边界和有限视觉采样，保留全片绝对位置与覆盖记录。

“粗索引”仍需读取较多媒体，不能理解为几乎没有成本。粗阶段减少的是高密度视觉推理与精细语义决策，不应删除未采样镜头的源区间索引。

字幕作为辅助需检查影片版本、语言和时间偏移。只有字幕可信且符合任务需求时才能替代部分 ASR 工作；不能默认字幕完整或与当前视频同步。

### 4.2 候选召回与精分析

根据剪辑目标找候选区间，再带相邻上下文检查真实对白、动作、人物和边界。必要时扩大依赖范围，不仅检查命中关键词的几秒。

低密度抽样可能漏掉短暂动作；应在评测中单独统计候选漏检。无候选不等于全片不存在目标事件。

最终脚本回查真实证据和合法片段 ID，不仅依赖多层摘要；摘要适合索引，不是原声或剧情真值。

### 4.3 分段规则

工程处理块与剪辑语义单元分开：

- 每块记录原视频 hash、分析版本、块 ID、全片绝对区间和局部时间映射。
- 分析输入可带邻接上下文，重叠部分在合并时按绝对时间及证据去重。
- 固定时长可控制工程处理规模，但不直接定义完整句子、动作或场景边界。
- 最终选择跨块完整单元；跨段人物、指代和因果依赖需额外检查。
- 用全局事件/人物引用辅助整合，但不宣称模型自动识别完全正确。

时长、重叠和采样密度依据素材与模型限制实测确定，不预先宣称某个分块参数最优。

## 5. 并发、缓存与阶段产物

### 5.1 有界并发

分别限制视频解码、ASR、本地 GPU、VLM/LLM API 的并发；资源不是同一种额度。

任务排队等待与实际执行时间分开。队列有上限，超容量明确拒绝或等待；长任务与短任务的公平性需压测，不能默认分段越多越快。

服务商 RPM、TPM 和并发限制可能同时存在，满足其中一项不代表满足全部。限流后同时重试会放大压力，需纳入调用调度预算。

### 5.2 合格产物复用

同一视频不同选题可复用探测、ASR、场景和可用视觉索引；决策与 QA 通常依赖新主题，不能直接复用旧结论。

缓存键包含内容 hash、阶段、分析/模型/配置版本及必要输入；产物保存覆盖情况、失败来源和完整性，不把半成品当完整缓存。

同一缓存键并发计算是否去重需要显式设计；用户权限仍需每次检查，缓存命中不能泄露其他用户素材。

### 5.3 恢复边界

阶段成功后保存不可变产物及校验信息，后续失败只重做必要阶段/块。

真正重启恢复需持久状态、产物引用、输入版本、领取与幂等推进机制；当前 LangGraph 编排和 Python 内存 job 不提供这些保证。Java MySQL 元信息也不自动恢复 Python 执行。

复用现有 Task 与报告存储扩展，不立即新增任务框架。没有恢复能力时只能如实保留当前进程产物或报失败，不能宣称可断点续跑。

## 6. 模型 API 超时分层

| 期限 | 控制对象 | 边界 |
|---|---|---|
| 连接/连接池等待 | 建立连接与获得连接 | 是否可配、具体语义取决于客户端 |
| 读取空闲超时 | 等待响应或下一段流数据 | 不等于整个调用总时长 |
| 单次调用总期限 | 请求开始至完整响应 | 流式持续输出也不能无限运行 |
| 阶段期限 | 本阶段调用、解析、修复及重试 | 重试不重新获得全额预算 |
| 任务总预算 | 排队策略、全部阶段、重试与迭代 | 排队期限与执行预算分别定义 |

各阶段使用剩余预算决定调用是否能开始与允许时长；没有足够预算则结束或返回合格候选，不启动注定越界的调用。

具体参数依据服务商限制、输入规模和真实延迟分布设定。读取超时语义、SDK 默认重试、流式行为需核实实际客户端，不能凭通用示例推断已配置。

流式响应改善首段可见性，但完整脚本必须等结束状态和全量校验；部分 JSON 不能直接进入可执行方案。

## 7. 错误分类与有限重试

| 情况 | 建议行为 | 注意 |
|---|---|---|
| 临时连接失败/可恢复网络错误 | 剩余预算内有限重试 | 连接错误也不能一概证明请求未执行 |
| 429 | 读取并遵守 Retry-After，受总预算限制 | 无预算则失败，不无限等待 |
| 可重试 5xx | 按服务商规则有界退避 | 不把全部 5xx 都当可恢复 |
| 等待响应超时 | 优先查询原请求状态（若支持），再决定重试 | 可能已执行/计费 |
| 参数/认证错误、权限/余额问题 | 明确失败，不循环重试 | 需要配置或用户处理 |
| 上下文超限 | 返回限制或启动已批准的分段路径 | 不能原请求反复重试 |
| 响应截断/非法结构 | 标记不完整/校验失败，有预算可修复或重试 | 不当成功脚本 |
| 无候选/语义风险 | 业务结果处理 | 不伪装成网络故障重试 |

退避包含随机抖动；次数、等待、输入/输出 token 与费用共享预算。SDK、HTTP和业务重试必须统一，避免叠加。

服务商提供幂等键、异步 job 查询或取消时使用其真实契约；不支持时只能约束本系统重复提交，无法保证服务商不重复生成/计费。

本地 requestId 不自动等于服务商幂等。重试也可能产生不同方案，不拼接两次请求的部分响应。

## 8. AgentCut 各阶段超时的处理建议

| 场景 | 已完成内容 | 处理 |
|---|---|---|
| VLM 超时 | 语音与时间索引 | 有足够证据可 ASR-only 并告警；视觉依赖任务不能假装完整 |
| 导演超时 | 已有合格分析产物 | 仅重试决策，或明确无脚本；不重新分析全片 |
| QA 超时 | 已有硬合格候选 | 输出 NEEDS_REVIEW，标记评审缺失，不假通过 |
| 修订轮次超时 | 此前硬合格候选 | 保留此前快照和对应风险，不覆盖为半成品 |
| 部分长视频块失败 | 成功块与覆盖记录 | 允许受限部分结果，但列未分析范围；不能说全片最优 |
| 任务预算耗尽 | 有/无合格候选 | 有则带限制交付，无则明确失败/无可用候选 |

“部分结果可展示”“可人工确认”“可自动执行”是不同状态。需要原意证据但仍缺关键区间的脚本不能自动准入。

不把超时降级成模拟口播，也不靠删上下文或超速兜底来掩盖任务失败。

## 9. 晚到结果、取消与版本一致性

每个模型调用建议记录调用 ID、阶段/块、任务 runId/attempt、inputHash、候选版本、服务商请求 ID（若提供）。

提交结果前检查任务仍接受该调用、attempt 与输入版本一致、未取消/终态；旧调用晚到只能按策略留诊断，不能覆盖新候选或人工版本。

本地超时意味着“不再接受该结果”，不必然终止后台线程或服务商推理。异步等待取消、线程执行终止、HTTP 断开、服务商任务取消必须区分。

超时后后台调用仍可能占用资源，不能立即释放逻辑并发额度再无限启动新请求而忽略真实存活调用。需要跟踪本地在途调用；服务商侧执行不可见时记录不确定状态与风险。

不承诺全链路 exactly-once。重复计算可能发生，目标是结果提交幂等与版本不被覆盖。

## 10. 工作台展示与成本记录

显示当前阶段、完成块数/覆盖区间、最后进展时间、等待重试、错误分类及是否有可用草稿。

心跳说明执行器存活，不证明阶段有进展；分别记录心跳、最近产物和阶段期限。长调用不靠进度不变一直延寿。

预计完成时间只在有历史统计时提供范围，不能假精确倒计时。计划分析范围、实际完成范围与失败块可查询。

成本记录包括每次调用与重试、输入/输出 usage、耗时、提供商和计价版本。未收到 usage 时记未知，不记零；无法确认的重复费用单列，可后续与账单核对。

## 11. 验证与验收

### 11.1 故障与机制测试

- 连接失败、首响应迟迟不来、流中断、持续流超过总期限。
- 429 含/不含 Retry-After、可恢复 5xx、认证失败、余额问题。
- SDK 自动重试与业务重试叠加，实际次数是否受上限约束。
- API 已执行但本地超时、旧结果晚到、用户重试生成新候选。
- JSON 截断、结束原因异常、Schema合法但区间/ID不合法。
- 一块失败、重叠块重复内容、跨块句子/人物依赖、缓存版本变化。
- 单进程线程未结束、资源槽位耗尽、多任务同时退避重试。
- 持久恢复只有实现后才能测试：重启、产物损坏、attempt冲突、重复结果提交。

### 11.2 真实效果指标

长视频：总/阶段耗时、资源峰值、API次数/费用、候选漏检、覆盖情况、失败重做量、人工定位与修正成本。

API稳定性：首次调用成功、重试后成功、超预算、限流、降级、失败与不确定结果，均报告分母；另报告尾延迟和重复费用未知情况。

内容：跨段上下文缺失、原意改变、对齐错误。速度提升不能抵消内容严重回归。

使用授权的不同长度素材对照指定范围、全片精分析和粗到细策略；预算不足时缩小实验，不只挑成功案例。未实际测试不得写耗时提升数字。

## 12. 与当前主线的推进顺序

1. 第一优先仍是短口播真实分析到合法脚本。
2. 模型调用先补期限、有限重试、预算、错误与来源可见、晚到结果拒绝。
3. 有复用需求后保存版本化阶段产物，区分当前进程复用与重启恢复。
4. 长视频先支持用户指定范围，观察耗时、边界和成本。
5. 再测试全片粗索引与候选精分析，最后考虑跨场景电影剧情剪辑。

这些是设计建议，具体阶段与实现范围仍需用户确认。本文未授权新增功能、修改仓库或提交 Git。
